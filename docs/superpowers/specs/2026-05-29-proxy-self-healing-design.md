# Автономная само-диагностика и само-лечение прокси (v1)

Дата: 2026-05-29
Статус: дизайн утверждён, готов к плану реализации

## 1. Цель и принцип

Бот ведёт себя как живой администратор прокси: непрерывно сам себя проверяет,
ставит диагноз, чинит то, что может безопасно починить, перепроверяет результат
и отчитывается админу. Главная задача — **стабильная работа прокси**.

Принцип безопасности: что обратимо и безопасно — бот делает сам; что требует прав
root/docker (перезапуск контейнера, смена конфига, перезагрузка сервера) — либо
уже автоматизировано через `autoheal`, либо бот присылает админу понятную
пошаговую инструкцию. Боту НЕ выдаются права docker/root: он принимает платежи и
пользовательский ввод, и такие права при компрометации бота отдали бы весь сервер.

## 2. Граница: что бот чинит сам, что эскалирует

**Чинит сам (мгновенно, без перезапуска прокси, полностью обратимо):**
- Основной маскировочный домен заблокирован, но в настроенном списке есть живой
  → бот переключает выдачу новых ссылок на лучший здоровый домен.
- На восстановлении основного домена — возвращает выбор обратно.

**Автоматизировано через autoheal (уже внедрено отдельно):**
- Зависший / упавший контейнер (`unhealthy`) перезапускается автоматически.

**Эскалирует админу с пошаговой инструкцией (бот сам сделать не может):**
- Легли **все** настроенные домены сразу.
- Похоже на блокировку **самого IP** сервера (домены с сервера живы, но трафика
  нет) — лечится сменой IP или добавлением доменов через меню `mtp`.
- TeleMT API недоступен дольше порога (уже есть отдельный монитор-алерт; этот
  дизайн его переиспользует, не дублирует).
- Требуется перезагрузка сервера / пересоздание прокси.

## 3. Сигналы детекции (только со стороны сервера, без внешних точек)

Честное ограничение: сервер стоит вне РФ и не видит блокировку своего IP изнутри
России напрямую. Поэтому используем косвенные серверные сигналы:

1. **Зондирование TLS-доменов** (надёжно, уже работает): `TLSDomainPicker`
   делает реальный TLS-handshake к каждому настроенному домену и хранит
   success_rate за последние 5 проб. Это основной сигнал.
2. **Доступность TeleMT API**: `telemt_client.is_available()` (уже есть).
3. **Трафик / число активных подключений** — *условный сигнал, под проверку*
   (см. §8). Если TeleMT отдаёт метрику подключений, «обнуление трафика при живых
   доменах» трактуем как подозрение на блок IP → эскалация. Если метрики нет —
   опираемся только на сигналы 1–2.

Домен считается **нездоровым**, если он был зондирован и его `success_rate < 0.5`.
Домен считается **здоровым**, если `last_ok == True` и `success_rate >= 0.6`.

## 4. Логика решений и предохранители

Фоновый цикл `self_heal_loop` каждые `SELF_HEAL_CHECK_INTERVAL` (по умолчанию 120 с):

1. Считать рейтинг доменов из picker и статус TeleMT.
2. Определить текущий «рекламируемый основной домен» (см. §5).
3. **Если основной нездоров и есть здоровая альтернатива** и не нарушены
   предохранители → переключить активный основной домен на лучший здоровый,
   записать время, уведомить админа, поставить флаг «ждём подтверждения».
4. **На следующих итерациях** перепроверить новый домен:
   - стал здоров и стабилен → отчёт «восстановлено», снять флаг;
   - тоже деградировал → **авто-откат** к настроенному основному + эскалация
     «все варианты плохие».
5. **Если все домены нездоровы** → авто-откат к настроенному основному (чтобы не
   зависеть от случайного выбора) + эскалация с инструкцией.
6. **Если домены живы, но трафик обнулился** (только при наличии метрики) →
   эскалация «возможен блок IP» с инструкцией.

**Предохранители (анти-дёрганье):**
- Кулдаун между переключениями: `SELF_HEAL_SWITCH_COOLDOWN` (по умолчанию 600 с).
- Лимит переключений в сутки: `SELF_HEAL_MAX_SWITCHES_PER_DAY` (по умолчанию 6);
  при превышении — только алерт, без новых переключений.
- Авто-откат при деградации выбранного домена.
- Анти-спам алертов: одно сообщение на проблему, повтор только при смене
  состояния (проблема исчезла / появилась новая).

Сердце логики — **чистые функции** без побочных эффектов, принимающие снимок
состояния (рейтинг доменов, текущий активный домен, время последнего
переключения, счётчик за день) и возвращающие решение (`keep` / `switch(to) /
revert / escalate(kind)`). Это делает логику тестируемой.

## 5. Переключатель домена (механизм)

Сейчас основная ссылка жёстко берёт `settings.tls_domain`
(`proxy_manager.pick_primary_tls_domain()`). Меняем так:

- В `TLSDomainPicker` добавляем **in-memory** поле `active_primary: str | None`
  и методы `set_active_primary(domain)` / `clear_active_primary()`.
- `pick_primary_tls_domain()` возвращает `picker.active_primary`, если он задан и
  валиден; иначе `settings.tls_domain` (текущее поведение).
- Ничего не пишется на диск и в конфиг прокси — переключение полностью обратимо.
  После рестарта бота поле сбрасывается; picker за пару проб (≤5 мин)
  пере-зондирует домены, и self_heal при необходимости переключит заново.

Прокси уже обслуживает весь список `tls_domains` одновременно, поэтому ссылка на
любой настроенный домен валидна без изменений на стороне прокси.

## 6. Сообщения админу (требование к качеству)

Каждое авто-действие и каждая проблема — это **человеческое** сообщение в Telegram,
понятное без техзнаний. Формат:
- **Что случилось** (простыми словами).
- **Что бот сделал сам** (если сделал).
- **Что нужно сделать руками** (если бот не может) — пронумерованные шаги с
  конкретными командами или пунктами меню `mtp`.

Примеры тона:
- Авто-починка: «⚠️ Домен `www.microsoft.com` перестал отвечать. Переключил выдачу
  ссылок на `www.cloudflare.com` — новые ссылки уже рабочие. Слежу дальше.»
- Восстановление: «✅ Домен `www.microsoft.com` снова стабилен. Вернул его как
  основной.»
- Эскалация (все домены легли): «❌ Все маскировочные домены недоступны с сервера.
  Сам исправить не могу. Сделайте: 1) `mtp` → 25 (проверить кандидатов доменов);
  2) добавьте 2–3 новых рабочих домена; 3) `mtp` → пересоздать прокси.»
- Эскалация (подозрение на блок IP): «❌ Домены живы, но подключений нет — похоже,
  заблокировали IP сервера. Нужно: 1) смените IP у хостера или 2) поднимите прокси
  на новом IP. Команды: …»

## 8. Открытый вопрос (проверить на живом сервере при реализации)

Отдаёт ли TeleMT API (`:9091`) метрику числа активных подключений (например,
`/v1/stats` или подобное). В коде сейчас используется только `/v1/users`. На этапе
реализации: запросить доступные эндпоинты у живого TeleMT и решить, включать ли
сигнал «трафик обнулился». Если метрики нет — фича работает на сигналах §3.1–3.2,
без обещаний по трафику.

## 9. Вне области v1 (YAGNI)

- **Массовая рассылка новых ссылок** всем активным пользователям при переключении
  домена — риск спама и rate-limit. Вместо этого новые запросы ссылок уже идут на
  здоровый домен, а кнопка «альтернативные ссылки» (уже есть) даёт пользователю
  рабочий вариант. Возможная v2.
- Авто-смена конфига прокси / IP сервера — только эскалация.
- Внешние точки проверки изнутри РФ (платный пробник) — отклонено пользователем,
  выбран бесплатный серверный вариант.

## 11. Тестирование

Тест-фреймворка в проекте нет — добавим минимальный (pytest) для чистых функций
решений в `self_heal.py`:
- основной нездоров + есть здоровый → `switch`;
- кулдаун активен → `keep` несмотря на нездоровый домен;
- превышен дневной лимит → `escalate`, без switch;
- все домены нездоровы → `revert` + `escalate`;
- выбранный домен деградировал → `revert` + `escalate`;
- восстановление основного → `keep` на основном (возврат).

Логика — чистые функции, поэтому тесты детерминированы и не требуют сети/Docker.
