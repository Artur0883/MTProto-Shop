# Multi-server failover (second proxy node) — design

Дата: 2026-05-29
Статус: дизайн утверждён, готов к плану реализации

## 1. Цель и принцип

Убрать единственную точку отказа. Сегодня весь шоп зависит от одного сервера/IP:
заблокировали IP в России или упал сервер — шоп лёг. Добавляем второй прокси-узел
на другом IP (другая страна), и клиент получает **две независимые ссылки**. Если
один IP недоступен — клиент подключается через второй. Это закрывает «Случай 2»
из дизайна само-лечения ([[changing-tls-masking-domains]], [[feedback-autonomy-with-guardrails]]),
который само-лечение в одиночку не решает.

Главный принцип: **сервер не пытается «угадать», заблокирован ли он в РФ** (он этого
не видит). Вместо этого у клиента несколько независимых входов, и он пользуется
живым — стандартный приём обхода блокировок.

## 2. Архитектура: один управляющий бот + прокси-узлы

- **Сервер A** (текущий, 31.76.77.226) — control plane: telemt-прокси + бот + база +
  support-бот. Единственный «мозг». Ничего не теряет.
- **Сервер B** (новый, другая страна) — **только прокси-узел**: telemt-прокси, без
  бота и базы. Просто вторая «дверь».
- Источник истины один (база и бот на A). B — управляемый узел, не самостоятельный шоп.

## 3. Приватный канал A↔B — Tailscale

API TeleMT (`:9091`, `read_only=false`) умеет заводить/удалять пользователей —
**нельзя выставлять в открытый интернет**. Бот на A управляет узлом B по приватному
каналу.

- **Tailscale** (на базе WireGuard): оба сервера ставят tailscale и логинятся одним
  auth-ключом → получают приватные адреса `100.x.x.x` и видят друг друга.
- Бот зовёт API узла B по его tailscale-адресу: `http://100.x.x.B:9091`.
- **Канал нужен только боту** (управление ключами на B). Клиенты подключаются к
  **публичному** IP узла B напрямую — на них канал не влияет. Если Tailscale моргнёт,
  существующие клиенты на B работают; отложится только заведение новых ключей (досверит
  reconciler, см. §6).

**Безопасность:**
- Трафик шифруется end-to-end (WireGuard); приватные ключи остаются на серверах;
  координатор Tailscale не видит содержимое.
- По каналу ходят только команды «создать/удалить ключ». Платежи и токен бота — на A,
  в туннель не попадают.
- **Firewall на B**: к порту `9091` пускать только tailscale-адрес сервера A. Даже
  компрометация tailnet не даёт доступ к API B с чужого адреса.
- Требование к админу: 2FA на аккаунте Tailscale.

## 4. Failover-модель (как это видит клиент)

- При выдаче доступа бот заводит ключ клиента **на всех узлах** (один и тот же секрет
  работает везде) и отдаёт клиенту **обе ссылки сразу**: основную (сервер A) и запасную
  (сервер B, помечена страной/меткой узла).
- Обе ссылки хранятся у клиента в Telegram. Заблокировали IP A — клиент переключается
  на ссылку B; B не зависит от A никак.
- **Ограничение MTProto:** ссылка жёстко привязана к одному адресу сервера, авто-прыжка
  A↔B в протоколе нет. Поэтому выдаём обе ссылки, клиент выбирает живую.

**Что покрывает / не покрывает:**
- ✅ IP сервера A заблокирован в РФ → клиент идёт через B.
- ✅ Сервер A как прокси заблокирован, но машина жива → бот всё равно работает (общается
  с Telegram наружу), клиент берёт ссылку B.
- ⚠️ Сервер A **умер целиком** → бот недоступен (он на A), но клиенты с уже выданной
  ссылкой B продолжают подключаться. Полное дублирование самого бота — вне области v1 (§10).

## 5. Единый установщик с выбором роли

Расширить установку (`install.sh` / меню `mtp`) выбором роли при запуске:
- `1) Основной сервер (бот + прокси)` — текущая полная установка.
- `2) Дополнительный прокси-узел` — ставит Docker + telemt-прокси (тем же образом) +
  Tailscale, поднимает firewall (открыт публично только 443; `9091` — только для
  tailscale-адреса A), и выводит свой tailscale-адрес для добавления в конфиг A.

Добавление узла = «запустил установщик → выбрал пункт 2 → ввёл auth-ключ Tailscale →
готово». На сервере A — пункт меню «Добавить прокси-узел» (ввести метку + публичный IP +
tailscale-адрес узла), который дописывает узел в конфиг и пересобирает бота.

## 6. Изменения в боте (control plane, всё на A)

1. **Конфиг — список узлов.** Новый параметр `PROXY_NODES` (JSON в `.env`, парсится
   pydantic в список моделей): каждый узел = `{name, public_host, api_url, primary}`.
   Обратная совместимость: если `PROXY_NODES` не задан — собрать один узел из текущих
   `SERVER_HOST` + `TELEMT_API_URL` (поведение как сейчас).
2. **TeleMT-клиент — на узел.** `api_call` принимает базовый URL узла; у каждого узла
   свой circuit breaker и сессия (узлы падают независимо).
3. **Выдача доступа.** `proxy_manager` заводит секрет клиента **на всех узлах**.
4. **Ссылки.** Строить ссылку на каждый узел; бот отдаёт основную + запасные (по узлам),
   помеченные `name`. Расширяет существующий UX альтернативных ссылок.
5. **Окончание/отзыв подписки.** Удалять ключ **со всех узлов**.
6. **Reconciler** (фоновая задача, как self-heal): раз в N минут сверяет состав ключей
   на каждом узле с активными подписками в базе; доводит (добавляет недостающие, удаляет
   лишние). Чинит расхождения, если узел был недоступен в момент выдачи/удаления.
7. **Мониторинг.** Следить за доступностью каждого узла (по его API); алерт админу при
   падении узла (как текущий монитор TeleMT, но по узлам).
8. **Админка.** В «Состояние системы» — блок по узлам: метка, доступен/нет, число ключей.

## 7. Взаимодействие с само-лечением

Ортогонально и складывается без конфликтов. Само-лечение переключает **маскировочный
домен** (одинаковый для всех узлов), второй сервер — это запас по **адресу/IP**. Домен
протух → переключается домен в ссылках всех узлов; IP узла заблокирован → клиент идёт на
другой узел. Picker и active-primary остаются как есть; в генерацию ссылок на каждый узел
подставляется выбранный домен.

## 8. Модель данных / состояние

Без новой таблицы per-user-per-node: reconciler выводит «кто должен быть на узле» из
существующей таблицы подписок и сверяет со списком ключей, который отдаёт API узла
(`GET /v1/users`). Состав на узле = идемпотентная проекция активных подписок.

## 9. Обработка отказов

- **Узел недоступен при выдаче:** завести на доступных, залогировать, не блокировать
  клиента (он получает ссылки на живые узлы); reconciler довыдаст на упавший, когда тот
  вернётся.
- **Узел недоступен при удалении:** удалить с доступных; reconciler удалит с упавшего
  после восстановления (истёкший ключ не должен «выжить» на узле).
- **Все узлы недоступны:** эскалация админу с инструкцией (как в self-heal).

## 10. Вне области v1 (YAGNI)

- Полное дублирование **бота/базы** (чтобы шоп жил при полной смерти A). Большой шаг,
  отдельный проект.
- Третий узел у другого провайдера (запас разнообразия) — добавляется тем же механизмом
  позже.
- Авто-смена IP / DNS-failover одной ссылкой — невозможно надёжно с MTProto.
- Балансировка нагрузки между узлами — не нужна на текущем масштабе.

## 11. Этапы (реализуем как два плана)

- **Этап 1 — инфра + установщик:** роль-выбор в установщике; на B — Docker + telemt +
  Tailscale + firewall; на A — Tailscale + firewall-правило. Критерий готовности: бот на A
  по tailscale-адресу делает `GET /v1/users` к API узла B и получает ответ. Бот ещё
  одноузловой.
- **Этап 2 — бот мульти-узел:** §6 целиком. Критерий готовности: новый клиент получает
  две рабочие ссылки; истечение удаляет с обоих; reconciler сводит расхождения; админка
  показывает оба узла.

## 12. Тестирование

- Чистые функции (юнит-тесты, как в self-heal): сборка списка узлов из конфига +
  обратная совместимость (один узел из SERVER_HOST); построение набора ссылок по узлам;
  логика reconciler (вход: активные подписки + список на узле → выход: что добавить/удалить).
- Интеграция узла B проверяется на живых серверах (этап 1: `GET /v1/users` через
  Tailscale; этап 2: реальная выдача → две ссылки → подключение).

## 13. Конфигурация (новые параметры)

```
# JSON-список узлов; если пусто — один узел из SERVER_HOST + TELEMT_API_URL
PROXY_NODES=[{"name":"A","public_host":"31.76.77.226","api_url":"http://mtproto:9091","primary":true},{"name":"B","public_host":"<IP_B>","api_url":"http://100.x.x.B:9091","primary":false}]
RECONCILE_INTERVAL=300
```
